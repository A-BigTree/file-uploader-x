# 方案 A：平台特定系统调用级监控 — 讨论纪要

> **日期**：2026-06-16
> **状态**：讨论中（未定稿）
> **参与约束**：基于"半受控部署 + 轻量级安全 + 生态优先"前提讨论
> **目标**：对外部动态库插件实现**系统调用级**运行时访问监控

---

## 一、背景与约束

### 1.1 当前架构现状

file-uploader-x 的插件采用 in-process 方式加载（`libloading`），插件运行在宿主进程地址空间内，可直接调用 `std::fs`、`std::net` 等标准库。宿主无法在 Rust 层面拦截这些调用。

相关代码位置：
- `file_uploader_core/src/pipeline/plugin.rs:106-127` — `Library::new` 加载动态库，无沙箱
- `file_uploader_sdk/src/models/ctx.rs:134-151` — `UploadFileData.data` 暴露完整文件内容
- `file_uploader_core/src/pipeline/plugin.rs:19-31` — 日志回调机制

### 1.2 本次讨论确认的约束

| 维度 | 选择 | 来源 |
|------|------|------|
| 部署模式 | 半受控（用户自主安装） | 陛下确认 |
| 安全方案倾向 | 轻量级（签名 + 白名单） | 陛下确认 |
| 文件访问目标 | 防止文件内容泄露 | 陛下确认 |
| 监控粒度 | **系统调用级** | 陛下确认 |
| 跨平台 | **必须全平台**（Linux / macOS / Windows） | 陛下确认 |
| 运行权限 | **无 root** | 陛下确认 |
| 监控用途 | **实时监控** | 陛下确认 |

### 1.3 约束冲突点（核心矛盾）

**系统调用级 + 无 root + 全平台 + 实时** 在技术上无法用单一机制完全实现：

- `eBPF`：需 root，且仅 Linux
- `seccomp`：需 root，仅限制不能监控
- `LD_PRELOAD`：Linux/macOS 可用，Windows 不可用
- `DLL 注入`：仅 Windows
- 内核审计 API：权限受限，跨平台差异大

**结论**：必须采用**差异化平台策略**——每个平台使用最适合的原生机制，通过统一抽象层对外暴露一致接口。Windows 上可能需要接受较低的监控精度。

## 二、方案 A 核心思想

### 2.1 设计理念

**差异化监控策略**：不同平台使用各自最适合的原生 Hook 机制，统一封装在跨平台抽象层之后，对上层 Pipeline 提供一致的 `AuditMonitor` 接口。

### 2.2 架构分层

```
┌─────────────────────────────────────────┐
│         应用层（Pipeline）                │
│    统一接口：AuditMonitor                │
└─────────────────┬───────────────────────┘
                  │
┌─────────────────▼───────────────────────┐
│         跨平台抽象层                      │
│   PlatformMonitor Trait                 │
└────────┬──────────┬──────────┬───────────┘
         │          │          │
    ┌────▼───┐ ┌───▼────┐ ┌───▼─────┐
    │ Linux  │ │ macOS  │ │ Windows │
    │  Hook  │ │  Hook  │ │  Hook   │
    └────────┘ └────────┘ └─────────┘
         │          │          │
    ┌────▼──────┐ ┌▼────────┐ ┌▼────────┐
    │LD_PRELOAD │ │DYLD_    │ │DLL 注入  │
    │   .so     │ │INSERT   │ │  .dll    │
    │           │ │LIBRARIES│ │(MinHook/ │
    │           │ │ .dylib  │ │ Detours) │
    └───────────┘ └─────────┘ └──────────┘
```

## 三、Linux 实现要点

### 3.1 机制：LD_PRELOAD

动态链接器在加载程序时优先加载 `LD_PRELOAD` 指定的共享库，该库中的函数覆盖 libc 同名函数。

### 3.2 实现关键点

1. **函数覆盖签名必须完全一致**，使用 `dlsym(RTLD_NEXT, ...)` 在构造函数中获取原始函数指针
2. **正确处理可变参数**（如 `open` 的 `O_CREAT` 模式参数）
3. **Hook 函数必须线程安全**（插件可能多线程调用）

### 3.3 需要拦截的系统调用清单

| 类别 | 系统调用 | 优先级 |
|------|---------|--------|
| 文件 | `open` / `openat` / `read` / `write` / `close` / `stat` / `fstat` / `access` / `readdir` | 高 |
| 网络 | `connect` / `send` / `recv` / `bind` / `listen` / `accept` | 中 |
| 进程 | `execve` / `fork` / `system` / `popen` | 高（高风险） |

### 3.4 macOS 差异

| 方面 | Linux | macOS |
|------|-------|-------|
| 环境变量 | `LD_PRELOAD` | `DYLD_INSERT_LIBRARIES` + 可能需 `DYLD_FORCE_FLAT_NAMESPACE` |
| SIP 限制 | 无 | System Integrity Protection 可能阻止注入系统进程 |
| 文件描述符路径 | `/proc/self/fd` | `fcntl(fd, F_GETPATH)` |
| 代码签名 | 不需要 | `.dylib` 可能需签名；需处理 ARM64/x86_64 双架构 |

**macOS 待解决风险**：SIP 可能限制 `DYLD_INSERT_LIBRARIES` 的有效性，需要实测验证在普通用户进程上是否可用。

## 四、Windows 实现要点

### 4.1 机制：DLL 注入 + API Hook

通过 Windows API 将监控 DLL 加载到目标进程地址空间，再用 Hook 库拦截 API 调用。

### 4.2 注入方式对比

| 方式 | 优点 | 缺点 | 适用 |
|------|------|------|------|
| 远程线程注入（`CreateRemoteThread` + `LoadLibrary`） | 通用 | 侵入性强，可能被杀软拦截 | 通用 |
| `SetWindowsHookEx` | 系统级钩子 | 需要窗口/消息环境 | GUI 场景 |
| 子进程启动注入（最简单） | 不需要跨进程注入 | 需要改变启动方式 | 推荐起步方案 |

**建议起步方案**：宿主启动时，将 Hook DLL 作为依赖加载到自身进程（因为插件是 in-process 的，注入到宿主进程即可覆盖插件调用）。

### 4.3 API Hook 库选择

| 库 | 特点 |
|----|------|
| **MinHook** | 轻量级，易于集成，推荐 |
| Detours | 微软官方，功能强大，许可需确认 |
| EasyHook | 支持 .NET/C++ |

### 4.4 需要拦截的 Windows API

| 类别 | API（A/W 两版本） |
|------|------------------|
| 文件 | `CreateFileA/W` / `ReadFile` / `WriteFile` / `CloseHandle` / `GetFileAttributesA/W` / `FindFirstFileA/W` |
| 网络 | `connect` / `send` / `recv` |
| 进程 | `CreateProcessA/W` / `WinExec` / `ShellExecuteA/W` |

**关键点**：必须同时 Hook ANSI（`A`）和 Unicode（`W`）两个版本。

### 4.5 Windows 已知局限

1. **COM 对象操作**（`IStream`、`IStorage`）无法通过 API Hook 拦截
2. **杀毒软件**可能拦截 DLL 注入，需数字签名
3. **监控精度**可能低于 Linux/macOS（需接受）

## 五、跨平台统一接口

### 5.1 PlatformMonitor Trait（讨论稿）

```rust
pub trait PlatformMonitor: Send + Sync {
    fn start(&mut self) -> Result<()>;
    fn stop(&mut self) -> Result<()>;
    fn subscribe(&self) -> mpsc::Receiver<AuditEvent>;
    fn has_syscall_monitoring(&self) -> bool;  // Windows 可能返回 false 或降级
    fn get_stats(&self) -> MonitorStats;
}
```

### 5.2 统一事件格式（讨论稿）

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct AuditEvent {
    pub timestamp: i64,
    pub plugin_id: String,
    pub syscall: String,        // "open" / "CreateFileA" 等
    pub path: Option<String>,
    pub arguments: HashMap<String, serde_json::Value>,
    pub result: Option<serde_json::Value>,
    pub duration_us: Option<u64>,
}
```

### 5.3 数据传输机制

Hook 层（C/C++）向宿主（Rust）传递事件的候选方案：

| 方案 | 优点 | 缺点 | 建议 |
|------|------|------|------|
| Unix Domain Socket | 实现简单，跨进程安全 | Windows 需用命名管道 | Linux/macOS 首选 |
| 共享内存 + 信号量 | 性能最高 | 并发复杂 | 高吞吐场景 |
| 文件映射（mmap） | 零拷贝 | 内存同步复杂 | 暂不考虑 |

**注意**：因插件是 in-process，Hook 实际运行在宿主进程内，事件传递可走进程内通道（如 `mpsc::channel`），无需跨进程 IPC，简化实现。

## 六、关键技术挑战与讨论结论

### 6.1 如何区分插件调用 vs 宿主调用？（待决）

Hook 拦截进程内**所有**系统调用，需区分哪些由插件发起。

| 方案 | 思路 | 评估 |
|------|------|------|
| 线程 ID 标记 | 插件执行前标记当前线程，Hook 中读取标记 | 推荐，开销小 |
| 调用栈分析 | 检查调用栈是否落在插件代码段 | 性能差，不推荐 |
| 分段 Hook | 插件执行前启用 Hook，执行后关闭 | 简单，但遗漏异步/后台线程 |

**待决**：是否接受"分段 Hook"在异步场景下的盲区？还是必须用线程标记？

### 6.2 如何处理插件的多线程/异步操作？（待决）

**风险**：插件启动的后台线程可能在插件 `execute` 返回后继续运行，绕过"分段 Hook"。

候选方案：
1. **进程级监控**：Hook 整个进程生命周期，记录插件创建的线程，`on_unload` 时警告未退出线程
2. **插件声明线程**：插件创建线程必须注册，宿主可跟踪/终止
3. **限制多线程**：通过 ABI 约束（过于严格，违反生态优先）

### 6.3 如何防止恶意插件绕过 Hook？（核心安全边界）

**攻击向量与防御**：

| 攻击向量 | 防御措施 | 在"无 root"下可行性 |
|----------|---------|-------------------|
| 直接 `syscall` 指令 | Hook `syscall` / 用 seccomp | seccomp 需 root，受限 |
| JIT 生成代码绕过 | 限制 `mprotect`、`dlopen` | 可部分限制 |
| 内存修改覆盖 Hook | 写保护 Hook 代码段 + 定期完整性校验 | 部分可行 |
| 内联汇编直接系统调用 | 难以完全防御 | 无法完全防御 |

**坦诚结论**：在"无 root + in-process"约束下，方案 A 能做到**显著提高攻击门槛**，但**无法保证绝对防御**。要达到强隔离，最终需要进程隔离或 WASM 沙箱（方案外）。

### 6.4 实时拦截 vs 事后审计（待决）

| 策略 | 行为 | 适用 |
|------|------|------|
| 实时拦截 | 敏感路径访问时立即阻断（`return -EACCES`） | 高危操作 |
| 事后审计 | 记录事件，稍后分析 | 普通操作 |
| 混合 | 敏感操作实时拦截，其余事后审计 | 推荐 |

**待决**：实时拦截可能误杀合法操作，是否需要白名单豁免机制？

### 6.5 如何保护宿主自身免受 Hook 影响？

候选：
- 选择性 Hook（仅插件上下文生效）
- 白名单路径（忽略系统目录）
- 配置化监控级别（开发模式详细 / 生产模式精简）

## 七、性能影响分析

### 7.1 预期开销

| 操作类型 | 单次系统调用额外开销 | 整体影响 |
|---------|-------------------|---------|
| Hook 函数本身 | ~5-10μs | — |
| 文件密集型插件 | — | 10-20% 性能下降 |
| 计算密集型插件 | — | <5% 性能下降 |

### 7.2 优化方向（待验证）

- 热点路径缓存（频繁访问的路径跳过检查）
- 事件批处理（非实时路径合并发送）
- 异步日志写入（不阻塞系统调用返回）

### 7.3 待执行的基准测试

- 插件执行期间系统调用频率统计

## 八、安全性自检

### 8.1 Hook 库自身的安全风险

| 风险 | 缓解 |
|------|------|
| Hook 库缓冲区溢出 | 优先用 Rust 实现 Hook 层；C 代码严格审计 |
| 恶意插件注入伪造事件 | 事件通道校验来源 |
| 拒绝服务（事件洪泛） | 速率限制 |

### 8.2 审计日志隐私

- 敏感路径（如 `~/.ssh/`）在日志中脱敏
- 日志级别可配置
- 日志文件建议加密存储（待决）

## 九、部署与维护

### 9.1 Hook 库分发方式

| 方式 | 优点 | 缺点 |
|------|------|------|
| `build.rs` 内置编译 | 单一分发 | 需 C/C++ 工具链 |
| CI 预编译多平台二进制 | 用户无需编译器 | 维护多平台 CI |
| 运行时首次编译 | 自适应 | 首启慢 |

**前提确认**：项目 CI（`.github/workflows/rust.yml`）需扩展支持 C/C++ 编译与多平台产物。

### 9.2 版本兼容性

- Linux：依赖 glibc 稳定 API，需测试主流发行版
- macOS：系统升级可能破坏 Hook，需持续验证
- Windows：API 更新风险较低，但需关注 ANSI/Unicode 版本

### 9.3 调试与降级

- 环境变量控制：`AUDIT_DEBUG=1`（详细日志）、`AUDIT_HOOK=0`（禁用 Hook 降级运行）
- Hook 初始化失败时应**降级而非崩溃**

## 十、替代方案排除理由

| 替代方案 | 排除原因 |
|---------|---------|
| eBPF | 需 root；仅 Linux |
| seccomp | 需 root；只能限制不能监控 |
| 虚拟机/容器 | 违反生态优先；部署成本高 |
| 完全进程隔离 | 属另一方案（方案外），本方案为轻量级 |

## 十一、与既有安全方案的衔接

方案 A 专注**运行时访问监控**，需与下列措施配合（分属其他讨论）：

1. **插件签名校验**（Ed25519）— 防止加载未授权插件
2. **路径白名单** — 限制插件加载来源
3. **最小数据传递** — 按权限决定是否传递文件内容
4. **Panic 保护**（`catch_unwind`）— 防止插件崩溃拖垮宿主
5. **权限声明**（`config.json` 中的 `permissions`）— 声明式权限

方案 A 是上述"声明式权限"的**运行时执行层**——声明权限是"契约"，方案 A 是"契约的监督"。

## 十二、开放性问题（待后续决策）

1. **监控精度 vs 性能**：是否接受 10-20% 的文件 IO 性能下降？是否需要可调节监控级别？
2. **线程标记 vs 分段 Hook**：异步场景盲区是否可接受？
3. **Windows 精度降级**：是否接受 Windows 上监控精度低于 Linux/macOS？
4. **实时拦截阈值**：哪些路径必须实时拦截？误杀容忍度？
5. **绝对防御边界**：在"无 root + in-process"下，接受"提高门槛而非绝对防御"的定位？
6. **Hook 实现语言**：Hook 层用 Rust（`#[no_std]` + 裸 FFI）还是 C？Rust 可提升自身安全性但增加复杂度
7. **CI 多平台构建**：是否已有/愿意扩展 C/C++ 编译能力？

## 十四、结论

方案 A 通过平台原生 Hook 机制实现系统调用级监控，是"无 root + 全平台"约束下最接近"系统调用级实时监控"目标的技术路径。

**核心结论**：
1. ✅ Linux/macOS 可实现较完整的系统调用级实时监控
2. ⚠️ Windows 需接受精度降级（COM 对象、部分绕过向量无法覆盖）
3. ⚠️ 在 in-process + 无 root 下，方案 A 是"提高攻击门槛"而非"绝对防御"
4. 🔜 需先做性能基准测试，确认 10-20% 文件 IO 开销是否可接受
